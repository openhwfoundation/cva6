# Running standalone simulations

Simulations run with `cook.py`. [flows/QUICKSTART.md](../flows/QUICKSTART.md#rtl-simulation) gives the sequences to copy (a first test, a whole testlist, the TestHarness, benchmarks, random tests, gate-level simulation) and [flows/README.md](../flows/README.md) the reference of every recipe.

Here is how you can run the hello world C program on the UVM testbench with VCS:

```sh
./cook.py hello-world -t cv32a60x -c gcc-15
./cook.py vcs-uvm-comp -t cv32a60x
./cook.py vcs-uvm-run -t cv32a60x -n hello-world
```

Without a commercial simulator, the TestHarness runs on Verilator for the AXI targets (`verilator-testharness-comp`, `verilator-testharness-run`).

The UVM testbench, with Spike in tandem, runs with the `vcs-uvm-*`, `xcelium-uvm-*` and `questa-uvm-*` recipes, and waveforms are enabled with `--trace-mode`.

## Running generated tests

Random tests are generated by [riscv-dv](https://github.com/chipsalliance/riscv-dv) with the CVA6 extensions of `verif/env/corev-dv`, then compiled and run on the UVM testbench against Spike. The tests of a target are listed in `config/target/<target>/verif/generated_test.yaml`; cv32a60x has one. With VCS:

```sh
./cook.py vcs-generator-comp -t cv32a60x
./cook.py vcs-uvm-comp -t cv32a60x --tandem-enabled
./cook.py macro-vcs-generator-testlist -t cv32a60x -c gcc-15 \
  -l config/target/cv32a60x/verif/generated_test.yaml --tandem-enabled
```

`-n <test>` runs a single test of the list, and `--seed` fixes the seed of the generator. The generated programs are in `build/cv32a60x/dv_generated/<test>/asm_tests/`. See the `vcs-generator-*` recipes in [flows/README.md](../flows/README.md) for the other options.

## Simulating with the RISC-V proxy kernel
When running C programs, a common requirement is to use standard library functions like printf. On a bare-metal core, these functions do not work because they rely on underlying system calls that have no operating system to handle them. The [RISC-V proxy kernel](https://github.com/riscv-software-src/riscv-pk) (pk) solves this: it loads the program and serves its system calls through the host, here the TestHarness (e.g. to properly display printf output).

The flow runs with cook.py, on the Verilator or VCS TestHarness, for a target with U-mode and the debug module. For instance on a 32-bit target:
```sh
./cook.py git-dependencies --repo riscv-pk
./cook.py pk-build -t fpga_linux_cv32a6 -c gcc-15
./cook.py pk-hello-world -t fpga_linux_cv32a6 -c gcc-15
./cook.py verilator-testharness-comp -t fpga_linux_cv32a6
./cook.py verilator-testharness-run -t fpga_linux_cv32a6 -n pk-hello-world
```
The program prints its text in `build/fpga_linux_cv32a6/simulation/sim_rtl_verilator_testharness/pk-hello-world/testharness.log`, confirming that the printf statement was executed properly. See the `pk-build` and `pk-hello-world` recipes in [flows/README.md](../flows/README.md) for the details.
